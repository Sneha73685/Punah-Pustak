# Development

The day-to-day contributor loop: which of the two supported ways to run the stack to reach for, what hot-reloads and what doesn't, and the handful of local footguns that have already bitten this project once (documented here so they don't bite twice). For the *what* of the stack itself, see [`../README.md`](../README.md#installation) (quick start) and [`deployment.md`](deployment.md) (full service breakdown, production topology). This document is the *how* of working in it day to day.

## Two ways to run the backend locally

Both are legitimate; pick based on what you're doing.

### 1. Full Docker Compose — the default

```bash
docker compose up
```

Migrations apply automatically — the `api` image's entrypoint ([`../backend/docker-entrypoint.sh`](../backend/docker-entrypoint.sh)) runs `alembic upgrade head` before every start, so there's no separate migration command after a fresh clone or a `git pull` that brought a new migration. See [`deployment.md`](deployment.md#automatic-migrations-on-startup) for why this is safe and what it replaced.

Everything (`db`, `storage`, `storage-init`, `api`, `web`) runs containerized. `api` bind-mounts `backend/app` and `backend/alembic`; `web` bind-mounts `frontend/src` and `frontend/index.html`. Editing a source file under either mount takes effect immediately — `uvicorn --reload` and the Vite dev server both pick it up with no container restart. This is the right choice for frontend work, for exercising the full stack end to end, and for anyone who doesn't want a local Python/Node toolchain at all.

**What does *not* hot-reload** — a rebuild is required:

```bash
docker compose build api   # after editing backend/pyproject.toml (new/changed dependency)
docker compose build web   # after editing frontend/package.json (new/changed dependency)
```

### 2. Backend outside Docker, database/storage still containerized

Useful for attaching a debugger to the API process, or for a faster edit/run loop than a container restart gives you. Bring up just the two stateful services, then run the API directly against them:

```bash
docker compose up db storage storage-init

cd backend
python3.12 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

cp .env.example .env
# edit .env: change DATABASE_URL and STORAGE_ENDPOINT_URL's host from
# db/storage (docker-compose's internal network names) to localhost —
# the two containers still publish 5432 and 9000 to the host.

alembic upgrade head   # this path runs outside Docker entirely, so
                       # docker-entrypoint.sh never runs — still a manual step here
uvicorn app.main:app --reload
```

The frontend can either keep talking to this locally-run API unmodified (same `localhost:8000`) or itself run outside Docker: `cd frontend && npm ci && npm run dev`.

**Creating the venv at exactly `backend/.venv`, not some other location or name, matters**: the mypy pre-commit hook (see [`../.pre-commit-config.yaml`](../.pre-commit-config.yaml)) invokes `backend/.venv/bin/mypy` directly rather than relying on an activated shell, so pre-commit's hook silently can't find mypy if the venv lives anywhere else.

## Before your first commit: install the hooks

```bash
cd backend
pip install -e ".[dev]"   # pre-commit is a dev dependency
pre-commit install         # from the repo root, or with -c ../.pre-commit-config.yaml
```

This wires Ruff, Ruff format, and mypy strict to run automatically on `git commit` for anything under `backend/` — the same checks CI runs, just moved earlier so a failure is a local, pre-push feedback loop rather than a red CI check. See [`../.pre-commit-config.yaml`](../.pre-commit-config.yaml) for the exact hook list; frontend checks aren't pre-commit hooks (run them manually, or rely on CI — see [`testing.md`](testing.md)).

## Common tasks

### Adding or changing a backend endpoint

Follow the layering [`architecture.md`](architecture.md) documents: router → service → repository → model, one module at a time. A service raises a `DomainError` subclass on failure; it never touches FastAPI types. A new unit test for the service should be able to run against a hand-written fake repository, with no database — if it can't, the change has probably leaked a persistence concern into the service layer.

### Adding a migration

```bash
cd backend
# after changing a model in app/modules/*/models.py
alembic revision --autogenerate -m "description"
# review the generated file by hand before committing — see database.md
alembic upgrade head
```

Every migration in this repository is hand-reviewed before merge, even when autogenerated — see [`database.md`](database.md#migrations) for why (enum names, cascade rules, and indexes need to be explicit and reviewable, not just whatever Alembic inferred). If a model change should produce *no* schema diff (e.g. a Pydantic-only response shape change), running `alembic revision --autogenerate` and confirming an **empty** diff is itself a useful check that the ORM model and intended change actually match.

### Regenerating frontend API types after a backend schema change

```bash
# with the backend running locally on :8000 (either method above)
cd frontend
npm run generate-api-types
```

Regenerates `src/api/schema.ts` from the live `/openapi.json`. Run `npx tsc --noEmit` immediately after — every place the frontend needs to catch up with the backend change surfaces as a compile error, not a runtime surprise. See [`frontend.md`](frontend.md#type-generation-workflow).

### Running the checks CI runs, locally, before opening a PR

```bash
# backend
cd backend
ruff check . && ruff format --check . && mypy app alembic tests
pytest

# frontend
cd frontend
npx tsc --noEmit
npm run test
npm run build
```

Full detail on what each of these actually verifies: [`testing.md`](testing.md).

## Known local-environment footguns

Two real issues surfaced during this project's own development, worth knowing about in advance rather than rediscovering:

- **Manual/browser testing against the Docker Compose stack pollutes the same database `pytest` uses, if you run the backend-outside-Docker setup with `DATABASE_URL` pointed at the same Postgres container Docker Compose's `db` service exposes.** pytest's per-test transactional rollback isolates what happens *inside* a test from other tests, but has no effect on rows committed by real HTTP requests during manual exploratory testing — those rows persist and can skew any test that counts rows rather than filtering to rows it created. If a `pytest` run starts failing on count/pagination-total assertions right after a manual testing session, this is the first thing to check. Fix: truncate the affected tables (`TRUNCATE users, listings, listing_images, refresh_tokens, admin_actions RESTART IDENTITY CASCADE`) and clear the MinIO test bucket before treating the next `pytest` run as meaningful — see `IMPLEMENTATION_SUMMARY.md`'s Milestone 3 section for the full incident.
- **Two host ports (`8000`, `5173`) are all `docker compose up` needs free.** If either is already bound by an unrelated project, bring up just `db`, `storage`, and `storage-init` (no port conflicts, since those publish `5432`/`9000`/`9001`) and run the API locally instead — see "backend outside Docker" above. This is a local-environment constraint, not a Compose problem to work around by editing `docker-compose.yml`.
